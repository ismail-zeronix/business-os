# 0007. AI intelligence layer: provider-independent, evidence-first, read-only first

**Status:** Accepted (2026-09-21). Architecture approved by the user. Stage 1 (core) and its tables approved 2026-09-21; it runs alongside the last steps of the customer Quotation (`docs/plans/paused/2026-09-21-ai-intelligence-core.md`). Data sharing (point 6) confirmed by the user the same day. Full design: `docs/ai-intelligence/`.

## Context
The application holds structured supplier evidence, price and stock observations, enquiries and customers. The team wants to ask questions in plain language and later get help with enquiries, broadcasts, sourcing and quotes. `CLAUDE.md` rules still apply: PostgreSQL is the source of truth, AI proposes and humans confirm, deterministic rules come before an LLM, and history is never overwritten.

## Decision
1. **A layer between the database and the screens, never a route around it.** `Question -> orchestrator -> permissioned tools -> context builder -> evidence package -> provider -> validated structured result -> screen -> audit`. The LLM has no database access, no raw SQL and no free tool execution. It only sees the evidence package built for the current request.
2. **Provider independence.** One `AIProvider` interface with adapters for Anthropic, OpenAI and Gemini, chosen on Settings > AI (admin only). Context, tools, prompts, the response schema and the style block are built and validated outside the adapters, so **changing provider changes neither the context nor the response style**. The user asked for multiple providers explicitly; this is an intentional exception to the `CLAUDE.md` line against them.
3. **Reuse, do not duplicate.** Evidence is `EvidenceSource` and the price and stock observations. Audit is `AuditLog`. Keys use `secret-box` (ADR 0005). Search is `searchProcurement`. No parallel evidence or audit tables.
4. **Read-only first.** In this scope the AI answers and drafts text. It creates and changes no business record and sends nothing. A future proposing module will write PENDING suggestions that a person confirms through the existing services.
5. **Permissions by capability.** Tools declare required capabilities and results are redacted to the actor's. Roles stay ADMIN and STAFF (ADR 0006), so both hold every capability today; new roles are a separate decision.
6. **Data sharing.** Text sent to a provider (product names, part numbers, supplier prices and stock, later enquiry and email text that may contain customer details) leaves the company's infrastructure. Mitigations: send only the evidence package for the request, never the database; redact by capability; keep supplier and customer text as delimited untrusted data; never send credentials; store summaries and IDs in execution logs, not raw commercial values; let the admin pick and change the provider. **Confirmed by the user (2026-09-21):** customer data may be sent to the chosen provider, for example to draft a customer email, **with a person in the loop**: a person sees what the AI produced before anything reaches a customer.
7. **Deferred by design:** agents, LLM extraction, suggestions with approve and reject, warranty and discovery fields, vector search, and any sending.
8. **Direct quote email is a later, opt-in trust level (user's direction, 2026-09-21).** Quotations plug into the AI layer as a plugin (a context provider plus tools), without rewriting the core. Once the user has confidence in the system, an admin may switch on a mode where the AI emails a customer directly with the quotation attached. Guardrails for that later stage: **off by default** and switched on only by an admin; only an **issued** quotation can be sent, attached **exactly as issued** (the AI never rewrites, re-prices or edits it); the covering text follows the Zeronix style; every send is audited with the quotation, the recipient and the text; there is no way to send supplier names or costs. Until then every customer message is a draft a person sends. There is no outbound email today (no SMTP), so this needs its own plan.

## Consequences
- Answers are only as good as the evidence. With sparse observations the AI says "unknown" and lists what is missing.
- Weaker models fail structured output more often. One repair retry, then a typed error; failures are visible in the execution log.
- Provider keys join `APP_SECRET_KEY` as high-value secrets; losing that key means re-entering provider keys.
- Later modules plug in through the tool registry, the context-provider registry and the prompt registry, without changing the orchestrator.
